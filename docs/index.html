Basalt

A WordPress block theme built for accessibility and search. Five style variations switch the whole look in one click, including a high contrast variation where every colour clears WCAG AAA. Structured data, breadcrumbs and the accessibility corrections live in a companion plugin, so they stay when you change theme. No build step, no external requests, and the theme itself ships no JavaScript.

Requirements

WordPress6.6 or newer
PHP8.1 or newer
BrowsersAny browser from 2023 onwards. The theme uses CSS logical properties, :has() and clip-path.
PluginsBasalt Core is included in the download and should be activated. Without it the templates still render, but there is no breadcrumb block and no structured data.

If the site runs below these versions the theme still renders, but an admin notice appears and nothing below the minimum has been tested.

Installation

  1. In WordPress go to Appearance → Themes → Add New → Upload Theme, choose basalt.zip and select Install Now, then Activate.
  2. Go to Plugins → Add New → Upload Plugin and install basalt-core.zip from the plugins folder of the download. Activate it.
  3. Optional: install basalt-catalog.zip the same way if the site needs a product or service catalog.

Uploading the wrong file

If WordPress reports a missing style.css, the full download archive was uploaded rather than the theme. Unpack it first and upload only basalt.zip.

First steps

Appearance → Basalt lists the four settings that matter on a new site and links straight to each.

1. Pick a style

Appearance → Editor → Styles. Five complete looks are included; switching one changes colours, type and spacing everywhere at once, and your own adjustments layer on top of whichever you choose.

2. Identity

Set the site title, tagline and logo. The tagline is used as the fallback meta description, so write it as a full sentence a search engine could show.

3. Header and footer

Both are template parts. Edit them once under Appearance → Editor and every template follows, including the navigation menu.

4. Who is behind the site

Settings → Search & Schema, added by Basalt Core. Business name, address, phone and opening hours. This is what produces knowledge panels and local results. Leave a field empty rather than guessing; wrong structured data is worse than none.

Adding your own

Copy a file from styles/ in a child theme, change the title and the values, and it appears in the Styles panel beside the others. Only redefine what actually differs; everything left out is inherited from theme.json.

Design system

Every colour, font size and spacing step is defined once in theme.json and used everywhere: front end, editor, patterns and block styles. Change a value and all four follow.

Prefer the design tokens over CSS

Edit them under Appearance → Editor → Styles, or in theme.json from a child theme for a change that survives a reset. Both the front end and the block editor follow.

Writing CSS by hand is only needed for layout work. A value set here stays editable in the Styles panel; a value written into a stylesheet does not.

Contrast when changing the accent

The accent carries white button text and is used for the focus ring. Pick a value with at least 4.5:1 against white for the text and 3:1 against the page background for the ring, or the theme stops meeting WCAG AA.

Type scale

Seven steps from x-small to display. Everything from medium upwards is fluid: it scales with the viewport between a minimum and a maximum, so no breakpoints are involved.

Spacing

Seven steps, 10 through 70. The larger steps are fluid as well, which is why a section that breathes on a desktop does not waste half a phone screen.

Writing CSS

The stylesheets are plain CSS in assets/css/ and are loaded in this order: base, layout, components, blocks, then a child theme's style.css. The theme's own style.css contains no rules, so a child theme always loads last.

Do not wrap theme CSS in @layer

WordPress prints the CSS generated from theme.json without a cascade layer, and an unlayered rule beats every layered rule regardless of specificity. Component styles placed in a layer lose every collision with theme.json: navigation links, the site title and buttons all fall back to the global link colour.

Where a rule has to win against a theme.json element style it needs a specificity above (0,1,0), because WordPress emits the link colour as :root :where(a:where(:not(.wp-element-button))). That is why the theme writes a.button rather than .button in those places.

Templates

All templates are block templates in templates/, editable under Appearance → Editor → Templates. Two of them are offered per page in the editor sidebar under Template.

TemplateBehaviourUse for
Default (page) Breadcrumb, title, featured image, content at reading width. Ordinary pages.
Landing page No breadcrumb, no title, no featured image, no width limit. Campaign and product pages built from patterns. The first pattern supplies the H1.
Full width Content spans the wide width, title kept. Overview pages, galleries, wide tables.

The remaining templates are chosen by WordPress: index, home for the posts page, single, archive, search and 404. Header and footer are template parts in parts/, shared by all of them.

One H1 per page

The Landing page template omits the page title on purpose, because the pattern at the top of the page already carries a heading. If you add a second H1 in the content on any other template, the page has two and both are weakened.

Navigation and template parts

A block theme has no menu locations and no widget areas. Header and footer are template parts, and everything in them is a block.

Choosing a header or a footer

Basalt ships five headers and four footers. They are template parts like any other, so you swap one for another rather than rebuilding it: in the site editor, select the header or footer block, open the toolbar and choose Replace. The list shows every part registered for that area. The swap applies to every template that uses that part, which is all of them.

Whichever you pick, the menu comes with it. None of these parts pins itself to a particular menu, so they all render whichever menu the site has and switching header does not lose it.

Every one of them was audited at 390, 768 and 1440 pixels: one banner, one main and one contentinfo landmark, no duplicate landmark names, no horizontal overflow, and no axe violations. Two navigation regions on one page are fine as long as a screen reader user can tell them apart, so the header menu is named Main menu and the footer menu Footer menu.

If you build your own, copy one of the files in parts/, add it to templateParts in theme.json, and give the outer group the class site-header or site-footer. Do not give it a header or footer tag: the template supplies that. A part that carries its own landmark tag produces two of them as soon as a plugin embeds it without saying which tag it wants, which is exactly what WooCommerce does.

The menu

The header contains a Navigation block. Select it in the site editor to add, reorder or nest items. Submenus open on click, which is what makes them usable by keyboard and on touch; the toggle is a real button with aria-expanded, and its target is 44 by 44 pixels.

Below 62rem the menu collapses into an overlay. That breakpoint comes from the Navigation block's own setting, not from the theme, so you can change it in the editor.

The footer

Three columns of ordinary blocks: site title and tagline, a navigation block, and a latest posts block. Replace any of them with whatever the site needs; nothing in the theme depends on their contents.

Breadcrumbs

The Breadcrumbs block comes from Basalt Core and is already placed in the templates that need it. It renders nothing on the front page, and it reads from the same data as the BreadcrumbList structured data, so the two cannot disagree.

Block styles

Selectable in the Styles tab of a block's sidebar: Card, Bordered and Section for groups; Card for columns as well, because a row of cards is more often three columns than three groups; Rounded and Framed for images; Checklist, Numbered steps and No markers for lists; Eyebrow and Underlined for headings; Testimonial for quotes; Tile for covers, which stretches the heading link over the whole block; Specifications for tables; FAQ item for details blocks.

Writing your own

A pattern is a PHP file in patterns/ with a header comment giving it a title, a slug and a category. Copy one of the existing ones and change it.

A new pattern file will not appear until the theme's pattern cache is cleared. WordPress caches the list of pattern files and the parsed theme.json, so a file you have just added looks as though it is being ignored. The switch core provides for this is a line in wp-config.php: 

define( 'WP_DEVELOPMENT_MODE', 'theme' );

With it set, both caches are skipped on every request. Take it out again on a live site: it is a development switch, not a setting.

SEO and structured data

The theme produces correct meta tags, breadcrumbs and Schema.org data without any plugin. If you install one, the theme detects it and stops emitting its own, so nothing is ever duplicated.

robots.txt and the AI crawlers

Under Settings → Search and schema there is a section called Crawling, robots.txt and AI. WordPress serves a virtual robots.txt with two lines in it; the theme adds the rules a normal site wants and one decision that is genuinely new.

Two different things share the label "AI crawler". Some collect text to train on and give nothing back. Others fetch a page because somebody asked a question and then name the source, which sends visitors, and for a local business those are turning into what a search result used to be. So the setting has three positions rather than a checkbox:

SettingWhat lands in robots.txt
Let all of them read the siteNothing. The default, because changing what a site tells crawlers is the owner's decision, not an activation side effect.
Only the ones that cite the sourceDisallow: / for the training crawlers (GPTBot, ClaudeBot, CCBot, Google-Extended, Bytespider and the rest). The citing ones (OAI-SearchBot, ChatGPT-User, Claude-User, PerplexityBot, DuckAssistBot, Applebot) stay welcome. What most small businesses want.
Keep all of them outBoth lists blocked.

The two lists are filterable through basalt_core_training_crawlers and basalt_core_citation_crawlers, so a new bot is one line in a child theme rather than a plugin update. Anything in Extra robots.txt lines is appended exactly as written.

A real robots.txt file wins

If there is a robots.txt in the site root, the server serves that one and nothing WordPress builds is ever seen. The settings screen says so with a warning when it finds one, because otherwise the setting simply appears not to work.

llms.txt

A plain text summary of the site at /llms.txt: what this is, the pages that matter, and how to get in touch. The format is a convention rather than a standard, which is exactly why it is worth serving. It is the one place where a site says in its own words what it wants to be quoted as.

Nothing in it is maintained twice. The title and tagline come from Settings, the address and hours from the schema fields, the page list from the pages that are published and not hidden from search engines. Cart, checkout, account and the privacy page are left out: they describe nothing about the business. The file is cached for twelve hours and thrown away when a page or a setting changes. It is served from a request handler, so no permalinks have to be flushed and nothing breaks if they are.

The two sentences at the top come from What this site is on the settings screen. Write them for somebody who has never heard of the business. The finished file can be rewritten through basalt_core_llms_txt, the page list through basalt_core_llms_pages.

Keeping something out of the index

Every post and page has a box called Search engines in the editor sidebar. Ticking it adds noindex, follow, takes the page out of the sitemap and out of llms.txt. The page stays reachable for anybody with the link, which is the point: a thank you page or a price list for one customer belongs online but not in a search result.

Three site wide switches sit next to it under Indexing:

SwitchWhat it does
Hide date archivesOn by default. On most sites they are the same posts listed a third time.
Hide author archivesOff by default. Worth switching on when one person writes everything.
Send attachment pages to the postOn by default. Every upload otherwise gets a page of its own with a title, an image and nothing else, competing with the post that uses the image.

All of it stands down when a dedicated SEO plugin is active, the same way the meta tags and the schema graph do.

Search Console and Bing

The verification codes go in the same section. Paste the code or the whole <meta> tag you were given; the code is taken out of it. The tags are emitted on the front page only, which is all either service looks at, and they survive theme updates because they are settings rather than a snippet in a template.

Opening hours

The hours you enter under Settings, Search and schema feed the LocalBusiness node, and they also feed the Opening hours block: a status line computed in the site's time zone ("Open today until 18:00", "Closed, opens Tuesday at 10:00") and a table in which consecutive days with the same hours share a row. One source, two outputs, so the visitor and the search engine are never told different things. The wording is filterable through basalt_core_opening_status and basalt_core_opening_rows.

The table groups the way a sign on the door does: days that open at the same time share a row, a day that stays open longer gets a short row of its own ("Thursday until 20:00"), a closed Sunday and Monday become one row. The block has two layouts, the table and a single line with short day names for a header strip.

FAQ structured data

Add a Details block, set its style to FAQ item, put the question in the summary and the answer inside. The theme reads the saved content and emits the matching FAQPage data. No shortcode and no custom block, so the content survives a theme switch as a plain accordion.

Answer the question in the first sentence

Search engines quote the opening of an answer. An answer that starts with background and reaches the point in sentence four is quoted from the background.

Verifying

Paste a URL into Google's Rich Results Test and the Schema Markup Validator. Both should show the graph with no errors. If you see two Organization nodes, an SEO plugin is emitting its own and was not detected: switch off structured data under Customize → Theme options.

Performance

What the theme does by default:

  • No web fonts. The system font stack renders instantly and costs zero requests. Add fonts through the WordPress Font Library if a brand requires them, and expect to pay for it in LCP.
  • No JavaScript framework, no jQuery. Two small deferred files, both observer based, with no scroll listener anywhere.
  • Core block styles load per block instead of one combined stylesheet.
  • The comment stylesheet loads only where comments render; the WooCommerce stylesheet only on shop views.
  • The featured image of a singular view is preloaded with fetchpriority="high", because it is usually the LCP element and core cannot see it in the template.
  • The emoji polyfill and its request to s.w.org are removed.
  • Speculative loading excludes carts, checkouts, account pages and any URL carrying a nonce.

Every one of these is filterable. See the hooks reference below if a specific site needs different behaviour.

What the theme deliberately does not do

Page caching, image conversion, database cleanup and CDN handling are plugin work. A theme that took them over would take them away again the day you switch theme.

Accessibility

Basalt targets WCAG 2.2 level AA. The theme is audited with axe-core across nine templates at 390, 768 and 1440 pixels, and reports zero violations with no horizontal overflow at any of the three widths.

What that covers:

  • Skip link as the first focusable element, pointing at a main landmark that can take focus. A skip link that moves the scroll position but not focus leaves keyboard users where they started.
  • Visible focus ring on every interactive element, drawn outside the element so it is never clipped. The High contrast variation widens it.
  • Submenus open with a real button carrying aria-expanded, and every control is at least 24 by 24 pixels, most of them 44.
  • Exactly one H1 per view, including the posts page, where the core query title block renders nothing and most block themes therefore have none.
  • Navigation and search landmarks carry accessible names, so a page with a header menu and a footer menu does not offer two entries called "navigation".
  • Eyebrow labels are paragraphs, not headings, so they do not appear in the document outline as sections that do not exist.
  • prefers-reduced-motion is honoured.
  • CSS logical properties throughout, so right to left languages need no second stylesheet.

Two things remain yours: alternative text on images, and keeping contrast above the threshold if you change colours. The editor marks an image with no alt attribute so it is caught before publishing.

A passing audit is not a conformance statement

Automated testing catches roughly a third of WCAG failures. It cannot judge whether your alt text is meaningful, whether your headings describe the content under them, or whether a form error message is useful. A theme can be conformant and a site built on it still is not.

Visitor display settings

Basalt Core can add a small button to the front end that lets a visitor adjust how the site is presented to them. Their choice is stored in their browser and applies on the next visit. Switch it on under Settings → Search & Schema → Visitor display settings; it is off by default, because a floating control is the site owner's decision to make.

SettingWhat it does
Text sizeScales the root font size to 115, 130 or 150 percent. Every size in the theme is relative, so the whole layout follows.
More space between linesRaises line height and paragraph spacing.
More space between letters and wordsApplies the values from WCAG 1.4.12. Helps when letters appear to run together.
Underline every linkMakes links identifiable without relying on colour.
Higher contrastApplies the same values as the High contrast style variation.
Reduce motionStops transitions and animations.
Do not keep the header on screenUnsticks the header, which matters at high magnification where a sticky bar can take a third of the viewport.

This is not an accessibility overlay

Overlays that promise automatic conformance are widely rejected by the accessibility community. They rewrite the DOM and inject ARIA at runtime, which interferes with the assistive technology a visitor has already configured, and they let a site owner believe the underlying problems are solved when they are not.

This panel changes presentation only. It adds no ARIA, rewrites no markup, and makes no claim about conformance. Everything it offers is something a visitor could also set in their operating system; it exists because many people do not know those settings are there.

The system settings win by default: prefers-reduced-motion and prefers-contrast are read as the starting values, and the panel departs from them only when the visitor asks it to.

Why there is an inline script

The preferences live in the visitor's browser, so they can only be applied once JavaScript has read them. A deferred script would apply them after the page has already painted at the default size, and the visitor would watch the text jump on every page load. A very small inline script in the head is the honest trade, and it is the only JavaScript on the page that is not deferred.

Login screen

Basalt Core can replace the WordPress logo and the default colours on wp-login.php with the site's own. Switch it on under Settings → Search & Schema → Login screen.

SettingNotes

The settings screen checks the colours you choose against WCAG AA and warns when the form text, the button text, the focus ring or the links below the form fall below the threshold. A colour picker that lets you build an unreadable login screen without saying so is a poor tool, and the login form is the one page where a user who cannot read the interface has no way around it.

Username enumeration

WordPress tells an anonymous visitor whether an account exists. Enter a username that is not registered and the login form says so by name; enter one that is and it complains about the password instead. That turns the form into a lookup service: an attacker confirms which accounts are real before spending any effort on passwords.

Switching this on makes both answers identical, on the login form and on the lost password form. The cost is real and worth knowing: someone who mistypes their username no longer learns that it was the username.

One case still differs

If the account exists but the site cannot send mail, WordPress reports that failure, and the two cases become distinguishable again. Hiding it would mean a site with a broken mailer telling every visitor their reset link is on the way while nothing is sent. A broken mailer is a misconfiguration to fix, not to mask.

What is deliberately not here

There is no custom CSS box. An administrator can already do more damage elsewhere, so this is not about privilege: a free-form CSS field on the login screen is a large surface for a small benefit, and it turns every future change to this page into a guess about what somebody pasted in.

There is no option to move the login URL either. Renaming wp-login.php quietens automated traffic in the logs and stops no attacker who looks at the REST API or an author archive, while reliably breaking integrations that post to the known address. A site that genuinely needs it needs a plugin dedicated to that job.

The login page is also given a main landmark, which core does not provide. That closes the only two accessibility violations the page reports, both of them core's rather than ours. It follows the branding switch, because it changes core markup and a site with custom login CSS written against a direct child selector would notice.

Demo content

Tools → Basalt demos. A demo fills an empty site with pages, posts, a menu and pictures so that you can see how the pieces fit together, then edit them into your own. It takes a few seconds and needs no other plugin.

Nothing is ever deleted

Importing only creates. A page whose address is already taken is left alone and reported, and no setting you have already filled in is overwritten. Every importer that offers to "replace" the existing content is one misplaced click away from removing work somebody had already done, so this one cannot do it. A demo that has been imported is not offered a second time, for the same reason.

Which also means the tidiest way to use it is on a site with nothing on it yet. On a site you have started, expect to be told that some of the pages were skipped.

The pictures

They are drawn during the import rather than downloaded or shipped: an abstract pattern of basalt columns in the theme palette, one per image, always the same from the same demo. Two reasons. A theme sold on a marketplace cannot redistribute photography it does not hold the rights to, and demo content is exactly where that goes wrong. And a placeholder that admits to being one is easier to find and replace than a stock photograph that half looks right.

Every one arrives with alternative text saying what it is. If the GD extension is missing, which is rare, the demo imports without pictures and says so.

The pages are patterns

A demo page is a handful of references to the patterns in the inserter, not a copy of them. So the demo cannot drift from what you get when you build a page yourself, and improving a pattern improves the demo. The one exception is the hero on the front page, which is written out, because a pattern is resolved when the page is rendered and cannot be handed the id of an image the import has just created.

Writing your own demo

A demo is one PHP file in demos/ inside Basalt Core that returns an array. There is no importer to write: the runner reads the declaration and creates what it describes. 

return array(
	'title'      => 'A studio',
	'front_page' => 'home',
	'images'     => array(
		'hero' => array( 'width' => 1600, 'height' => 1000, 'seed' => 3, 'title' => 'Hero', 'alt' => '...' ),
	),
	'posts'      => array(
		array(
			'type'     => 'page',
			'slug'     => 'home',
			'title'    => 'Home',
			'template' => 'page-landing',
			'content'  => '<!-- wp:pattern {"slug":"basalt/hero-centred"} /-->',
		),
	),
);

Two tokens are available in content: {{url:slug}} for a link to another page in the same demo, and {{image:key}} for one of its images. Both exist because neither value is known until the import is running.

A post whose type is not registered is skipped rather than failing, so a demo can declare catalog entries and still import correctly on a site without Basalt Catalog. Filter basalt_core_demos to add a demo from somewhere other than that folder.

Plugins

Basalt has been built and tested against the plugins a site is most likely to already have. Everything below has been run in a real install, and each entry says what the theme actually does. Nothing is listed as "compatible" on the strength of having read its documentation.

Basalt Security

The security a small site needs, without the weight the category is known for: no scanner, no cron job, no dashboard of graphs, and nothing written to the database on a normal page view. Settings live under Settings → Security.

  • The login page moves. Pick an address and wp-login.php answers 404 for everybody, including the bots that make up nearly all login traffic. Every link WordPress builds, including the ones in password emails, is rewritten to the new address. wp-admin answers 404 for visitors who are not signed in, rather than redirecting to the login page and giving the address away; admin-ajax.php and admin-post.php stay open.
  • Lockout after repeated failures. Per address, not per account, because locking an account is what an attacker wants. Each further lockout doubles, up to a day. No artificial delay: a sleep() holds a PHP worker, and a handful of attackers could then take the site down with the protection itself.
  • A short list of patterns. Traversal, union select, script tags in a URL, requests for .env or an old phpunit runner. The URL is always checked; a submitted form only for visitors who are not signed in, so an editor pasting a code sample is never blocked.
  • Headers. nosniff, a referrer policy, a permissions policy, X-Frame-Options and a narrow content policy. The policy deliberately says nothing about scripts: a script policy needs a nonce per response and breaks the moment a page is cached at the edge.
  • The other three doors into an account. The password reset form is limited per address, because every request sends mail to an inbox a stranger typed. The registration form gets a hidden field no person fills in, a limit per address, and an answer that does not confirm which addresses already have an account. Both cover the WooCommerce forms as well, which run their own registration and never reach the WordPress hooks. Resetting a password ends every session on the account, which is the point of resetting it.
  • Signing in with a link. Off by default. A customer signs in twice a year, cannot remember the password, resets it and picks something worse: a link proves the same thing the reset proves, in one step instead of four. The token is single use, expires in fifteen minutes and is stored only as a hash, so a database dump is not a pile of working sign in links. The link opens a page with a button rather than signing anybody in by itself, because mail scanners follow every link in a message and a token a scanner can spend is gone before the person clicks it. Administrators are left out unless you say otherwise, the answer never reveals whether an address has an account, and it stands down entirely while a lockout is in effect.
  • Passwords that are not obvious. Length, and nothing built around the site name or the account name. No rule about capitals and digits: that rule produces Sommer2026! and nothing safer. Twelve characters by default, and the message says why a short sentence beats a short password.
  • Hardening. XML-RPC off (and /xmlrpc.php answers nothing at all), no user enumeration through ?author=1, the REST users endpoint or the sitemap, no theme and plugin editor, no version number in the markup, application passwords for administrators only.

Locked out? define( 'BASALT_SECURITY_LOGIN_SLUG', '' ); in wp-config.php puts the login page back at its usual address, and define( 'BASALT_SECURITY_OFF', true ); switches the whole plugin off without touching the database.

What this installation still leaves open

Below the settings the same screen lists what is wrong before the plugin is involved: a site still on plain HTTP, PHP notices printed into the page, a debug log sitting in a public folder, an account actually called admin, a writable wp-config.php, a PHP version past its last security fix. Nothing on that list is changed for you. Half of it belongs to the host or to wp-config.php, and a plugin that silently changes those is a plugin that breaks a site at three in the morning. It says what, why and where, and then gets out of the way.

The OWASP Top Ten, and where each one is handled

The theme and its plugins were gone through against the list. Most of it is not a feature but an absence: no direct database queries, no unescaped output, no remote requests, no file uploads, no third party code to keep patched.

RiskWhere it is answered
A01 Broken access controlEvery admin screen behind a capability, every form behind a nonce, saved data always written for the current user rather than a user id from the request. The account pages read get_current_user_id() and nothing else.
A02 Cryptographic failuresNothing is encrypted or hashed by the theme. Form tokens are HMACs over the WordPress salts; the review screen flags a site that is not on HTTPS and an admin area that does not require it.
A03 InjectionNo SQL is written anywhere: everything goes through WP_Query and the meta API. Output is escaped at the point of output. Mail headers are built from a validated address, and the name in front of it cannot become a second header.
A04 Insecure designRate limits on every public form (contact, feedback, registration, password reset), a honeypot instead of a captcha, a depth limit where a reusable block could otherwise contain itself, and a size limit on everything written to user meta.
A05 Security misconfigurationThe headers, the hardening switches, and the review list for the parts a plugin should not change on its own.
A06 Vulnerable componentsNo bundled libraries, no build output, no vendor directory. The only dependency is WordPress.
A07 Authentication failuresLockout per address, the login page moved off the address the bots know, generic answers on login and password reset, no enumeration through ?author= or the REST users endpoint, password quality on every form that sets one, all sessions ended on reset, application passwords for administrators only.
A08 Integrity failuresNo unserialize, no eval, no code downloaded at runtime. The demo importer is behind a capability and a nonce and only ever reads files that ship with the plugin.
A09 Logging failuresLockouts, blocked requests, sign-ins, rate limited resets and registrations are written to a short log on the settings screen. A hundred lines, not autoloaded, no personal data beyond the address that made the request.
A10 Server side request forgeryNothing here fetches a URL. Redirects go through wp_safe_redirect, so a redirect target from a request cannot leave the site.

What this is not

There is no malware scanner, no firewall with a rule feed and no two factor authentication. A scanner that runs on the same server as the thing it is scanning finds what it is told to look for; two factor authentication is worth having and belongs in a plugin that can also handle recovery codes and a lost phone. Both are honest gaps rather than oversights.

WooCommerce

Supported. WooCommerce brings its own block templates for the shop, the product page, the cart and the checkout, and Basalt uses them rather than shipping copies: those templates change between WooCommerce releases, and a theme that copies them inherits the maintenance without giving you anything you can see.

What the theme adds is the part WooCommerce cannot know about. Wherever WooCommerce still renders through its classic templates it opens a second main element, and since the surrounding block template has already opened one, the page ends up with two main landmarks. That fails WCAG and leaves a screen reader user guessing which one holds the content. Basalt replaces that wrapper with a plain div, so the styling hook survives and the landmark does not. It also brings WooCommerce's buttons and the show password toggle up to the 44 pixel target size the rest of the theme uses, and styles its tables, notices and checkout fields with the theme's tokens.

The mini cart drawer correction lives in Basalt Core rather than in the theme: WooCommerce prints that drawer on every page of a store with aria-hidden="true" around six focusable controls, and nothing takes them out of the tab order. It is a problem under any theme, so it is fixed where it will survive changing theme.

Basalt Shop

A companion plugin for a shop that also has a counter. A product marked In store only on its General tab stays visible, keeps its page and its place in the grid, but cannot be bought online: the cart button and the add to cart form become an appointment button with a sentence you write yourself, the price can be hidden, and the Offer in the structured data is marked InStoreOnly so search engines are told the same thing. Settings under WooCommerce, Settings, Products, In store: the appointment page, the button label, the text.

The plugin also adds the Attribute range block for the product grid: the span of one or more attributes in a line, such as "70 to 90 · Cup B to G", so a shopper sees whether her size is in the range before opening the product. Attribute slugs are entered comma separated, the first one without its label.

The buy bar

A product page on a phone is a long column, and the button that sells the thing scrolls out of sight in the first second. The buy bar keeps the name, the price and one button at the bottom of the screen on displays narrower than 782 pixels. Switch it off under WooCommerce, Settings, Products, In store.

It is not a second add to cart form. A second form means a second set of variation selects, a second quantity field and two states to keep in step. The button belongs to the form that is already on the page, through the HTML form attribute, so pressing it is the same event as pressing the real one. What the button does depends on what the product is:

ProductThe button
Simple, in stockAdds to the cart, exactly as the real button does.
Variable or groupedSays "Choose your size" and takes the visitor to the form. A size cannot be skipped, and a button that pretends otherwise produces the wrong order.
In store onlyThe appointment button.
ExternalThe link to the other shop.
Out of stockNo bar at all.

Without JavaScript the bar is simply always there on a narrow screen. With it, the bar waits until the real button has scrolled past and slides out of the way again when it comes back.

Filtering reviews by size

On a shop where size is the whole question, the useful review is not the most recent one, it is the one written by somebody the same size. The Review filter block puts a row of sizes above the reviews, taken from what reviewers said they wear, with a second row for how the size came out.

Each one is a link: the same page with a query argument on it. A filtered view therefore has its own address, can be sent to somebody, works with the back button and needs no JavaScript. The filtering happens in the comment query itself, so it applies to the classic review template and the review block equally, and WooCommerce's pagination keeps working because it is the same query. The block renders nothing until two different sizes have been named, which is the point at which a filter starts to be worth having.

The cart drawer

The Cart drawer block belongs in the header. It is a button with the number of items, and a panel that slides in from the side with the contents, the subtotal and the two links out: the cart page and the checkout.

WooCommerce has a mini cart block of its own and it is a small application: its own store, an interactivity runtime, a rendering layer, several hundred kilobytes of JavaScript for a list of three items. This one is a details element with the cart rendered into it on the server. It opens and closes without JavaScript, the remove links are ordinary links with a nonce, and after adding something the panel is simply rendered open. What the script adds is the manners: escape closes it, a click on the dimmed page closes it, the focus goes in and comes back, and when WooCommerce adds to the cart over its own API without reloading the page, the panel fetches its own contents again so the number in the header is never a lie.

A remove link comes back to the page the visitor was on rather than to the cart page: taking something out of the cart is not a reason to leave the product they were reading about.

A cart in the markup is personal data

A page containing this panel must not be served from a shared cache. WooCommerce sets the cookies a sane cache looks at, and the plugin sets DONOTCACHEPAGE once there is something in the cart. An empty cart renders an empty panel, which is safe to cache.

Contact Form 7 and WPForms

Supported. The theme's input, label and focus rules are written with :where(), so both plugins inherit them without being asked. What is left is what each one sets itself.

Contact Form 7 ships almost no styling on purpose, so its submit button arrives as the browser default and its fields come out around 375 pixels wide whatever the column is. Basalt gives the button the theme's button, makes the fields fill their column, and darkens the validation red, which sits just under AA on white.

WPForms ships a full design and exposes it through custom properties. Basalt maps those onto its own colours, corner radii and the 44 pixel target size. It is the supported way in, so anything you restyle in the WPForms settings still wins.

These rules load on exactly the pages where the plugin has loaded its own stylesheet. That is the plugin's decision, not the theme's, and the two do not currently agree: WPForms loads per page, Contact Form 7 on every page.

Gravity Forms is not on this list. It ships its own design system with its own token layer and is styled through that, and being commercial it cannot be tested against before release. A rule written blind against markup nobody has run is worse than no rule.

Basalt Forms

The reason a site installs Contact Form 7 is one form, and this plugin is that one form. A Contact form block with name and email always, and phone, topic, preferred date and message as you switch them on. Every label is an attribute, so you write them in your own language in the editor. Validation happens on the server with the message at the field, the invalid control carries aria-invalid and points at its message, and there is no JavaScript at all. A honeypot and a rate limit of five messages per address and hour keep the spam out. Every submission is mailed and also kept under Form entries, because mail from a shared host does not always arrive.

The form carries a stable token rather than a nonce on purpose: a nonce expires, and a contact page is exactly the page a cache keeps for days.

Elementor

Basalt does not integrate with Elementor, and this is deliberate. Elementor is not a plugin a theme supports, it is a plugin that replaces the theme: registering its theme locations would hand templates/ to Elementor Pro's theme builder, and none of the accessibility work in this theme would still be reachable. A default Elementor page also ships several hundred kilobytes of JavaScript before the first theme asset, which is the opposite of what Basalt is for.

What the theme does guarantee is that an Elementor page renders correctly. Elementor's root element is given the block layout system's alignfull, so it gets the full width of the content area and Elementor decides the width of its own sections. Without that, a full width Elementor section comes out as a narrow column.

Set your global colours in Elementor before you build anything. Elementor's untouched default kit uses a light blue, a mid grey and a green that fail contrast on a white background: the default heading colour measures 2.01:1 where 3:1 is required. The theme does not overwrite them, because a customer who has chosen brand colours in Elementor would lose them without being asked. Site settings, Global colours, in the Elementor editor.

Classic Editor

Supported, and it is worth knowing why that needed saying. Classic Editor is on ten million sites, and a site that imports older content has post_content full of plain HTML with no block classes on it. Headings, lists and paragraphs are fine, because those are styled as elements. Quotes and tables are styled per block, so a blockquote written in the classic editor arrived with no quotation mark of any kind and read as an ordinary paragraph, and a table arrived unbordered and wider than the column it was in. Both are styled now, with :where() and scoped to elements carrying no class, so a real block always wins.

Caching and optimisation

LiteSpeed Cache, WP Rocket, Autoptimize and SiteGround Optimizer move, defer and bundle inline JavaScript. Basalt Core has exactly one inline script, the one that applies a visitor's saved display settings before the first paint, and it carries the exclusion markers all four read (data-no-optimize, data-noptimize, data-cfasync). If it were deferred the page would paint once unadjusted and then jump, in front of the person who turned the setting on because the default was hard to read.

Verified rather than assumed: with LiteSpeed Cache set to minify, combine and delay JavaScript, nineteen scripts on the page were rewritten and two were converted to delayed execution. The boot script kept its attributes, its position in the head and its ordinary type.

Login security plugins

Wordfence, Limit Login Attempts Reloaded and Really Simple SSL were run against the branded login screen, including the lockout state, which is the one that actually renders extra markup. Nothing needed correcting: the error notice keeps core's own colours, which stay legible whatever page background you choose, because it carries its own.

Their messages are not rewritten by the generic error setting either. That setting replaces the message that says whether an account exists; a lockout message says nothing about the account, so it is left alone and the visitor still learns why they cannot get in.

SEO plugins

Rank Math, Yoast, SEOPress, All in One SEO, Slim SEO and Squirrly are detected. Basalt Core hands over the parts each of them owns, so nothing is emitted twice. See SEO and structured data.

Translation plugins

WPML, Polylang, TranslatePress, Weglot and GTranslate are detected, and they own exactly one thing Basalt Core would otherwise be tempted to emit: hreflang. Basalt Core emits none of its own. A site with one language does not need it, and a site with several has one of these installed, which is the only thing that knows which URLs are translations of each other. A self-referencing hreflang from a theme would be noise on a monolingual site and a contradicting second answer on a translated one.

Consent banners

The two leading ones behave very differently, so they are treated differently.

CookieYes is clean as it ships and needs nothing: focus reaches the banner first, its controls are 44 pixels tall, the focus ring is visible, contrast passes, and rejecting is as prominent as accepting.

Cookie Notice & Compliance is corrected. It paints the accept and reject buttons in a colour from its own settings and leaves the label white whatever that colour is, so its default gives 2.93:1 where 4.5:1 is required, on the primary control of a banner a site is obliged to make usable. Basalt Core leaves the background alone, because it is a colour somebody chose, and moves only the label to whichever of near black or near white can be read on it. Pick a dark button and the white label stays and the rule is never emitted. The correction is applied on the login screen too, where the banner also renders.

Complianz could not be audited, because its banner does not appear until its setup wizard has been completed. Nothing is claimed about it.

There is one collision worth knowing about. A bottom anchored consent banner covers the display settings trigger on a phone: measured with both CookieYes and Cookie Notice at 390 pixels wide, each reaches the bottom edge and the trigger sits underneath it, so a tap lands on the banner. The trigger stays in the tab order, so it is never unreachable by keyboard. If it affects your site, move the trigger with the offset property rather than waiting for a theme update: 

@media (width <= 767px) {
	body:has(.cky-consent-container) { --basalt-a11y-trigger-offset: 21rem; }
	body:has(#cookie-notice) { --basalt-a11y-trigger-offset: 8rem; }
}

Those two numbers differ by more than 200 pixels, which is why no value is set in the theme. The height of a consent banner depends on its own text, and a number guessed against one version of one plugin is a rule that silently stops being true.

Child themes

A ready child theme is included in examples/basalt-child/ with its own README. Copy the folder, rename it, keep Template: basalt.

The parent enqueues the child's style.css last, so there is no enqueue boilerplate to write.

Prefer theme.json and styles/ in the child over CSS for anything visual: values defined there stay editable in the Styles panel, and CSS written by hand does not.

Overriding a template

Copy the HTML file into the child theme at the same path. A child theme can also add templates the parent does not have, such as templates/single-product.html for a custom post type.

Replacing a whole module

add_filter( 'basalt_modules', function ( $modules ) {
    // Drop a module you want to replace wholesale.
    return array_values( array_diff( $modules, array( 'performance' ) ) );
} );

Translation

The theme is fully translatable. languages/basalt.pot contains every string.

  1. Open the POT file in Poedit and create a translation for your language.
  2. Save it into languages/ as de_DE.po and de_DE.mo, matching your site's locale.
  3. Set the site language under Settings → General.

Put translations in a child theme's languages/ folder to keep them safe from theme updates. WordPress loads a child theme's translations before the parent's.

The plugins, and German

All five plugins are translation ready in the same way, each with its own POT in its own languages folder. German is included: a de_DE catalogue per plugin, as .po, .mo and the .php format WordPress 6.5 and later loads fastest. Set the site language to Deutsch and everything the plugins print is German, front end and admin.

The German is written in the polite form. A catalogue that ships with a product cannot know whether a site says du or Sie to its visitors, and the polite form is the one that is never wrong. A site that wants the informal form does not edit the catalogue, which the next update would overwrite: it filters gettext in its child theme and maps only the sentences it says differently, which is usually a dozen rather than three hundred.

Another language, without editing a .po by hand

  1. Regenerate the POT if the code has changed: wp i18n make-pot plugins/basalt-core plugins/basalt-core/languages/basalt-core.pot --domain=basalt-core
  2. Put the translations in a JSON file, one "original": "translation" pair per string.
  3. node tools/make-po.mjs <pot> <json> <out.po> <locale>. Whatever has no translation is listed rather than quietly shipped in English.
  4. wp i18n make-mo <dir> and wp i18n make-php <dir>.

Keeping the translations in JSON rather than in the .po is what makes a regenerated POT harmless: strings that still exist keep their translations, and new ones show up as missing instead of disappearing.

Right to left languages need no separate stylesheet. The theme uses CSS logical properties throughout, so the layout mirrors on its own.

Troubleshooting

Menu links are the wrong colour after changing Styles

The link colour under Styles applies to every link on the site, including the header. Set the navigation colour separately, or override .menu-item > a in a child theme's stylesheet.

Two sets of meta tags in the page source

An SEO plugin is active that the theme does not recognise. Switch off the theme's own output under Customize → Theme options → Search engines, or add the plugin to the detection list with the basalt_seo_plugin_handles filter.

Custom post type archive returns 404

Rewrite rules have not been flushed. Open Settings → Permalinks and save without changing anything.

The sidebar does not appear on a page

Pages have no sidebar by default. Select the With sidebar template, and make sure the Sidebar widget area is not empty.

Structured data warnings about missing fields

Google reports optional fields as warnings, not errors. Warnings about aggregateRating or offers on a Product mean those fields are absent, which is correct when the site does not publish prices or reviews. Do not invent values to silence them; fabricated structured data earns a manual action.
